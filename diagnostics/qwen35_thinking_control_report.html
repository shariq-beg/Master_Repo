Can You Control
Qwen3.5:9B Thinking?

A 28-case systematic test of every documented method to suppress or enable hidden reasoning in Qwen3.5:9B — and why most of them silently fail.

Model: qwen/qwen3.5-9b Quantization: Q4_K_M Runtime: LM Studio 0.4.x Endpoint: 127.0.0.1:1234/v1 Cases: 28 max_tokens: 300
// TL;DR

Bottom line: Across 28 systematic test cases, Qwen3.5:9B running under LM Studio's OpenAI-compatible API produced reasoning output (reasoning_content) in every single case — even when thinking was explicitly disabled. Only 4 of 28 cases yielded any visible answer at all. The model appeared to accept every control parameter without error, but "accepted" does not mean "honored."

// Methodology

How the Test Was Designed

A fixed prompt ("What is the best way to explore Sydney in one day?") was sent 28 times — the same prompt crossed against every combination of system-prompt handle and API body parameter. The model was served via LM Studio 0.4.x using a Q4_K_M quantized GGUF, accessed through the local OpenAI-compatible endpoint.

Scope note: All system-prompt handles were placed in the system message only. Placing /no_think in the user message — a variant that reportedly worked for some Qwen3 users — was not tested here and is a priority for a follow-up experiment.

System Prompt Handles (4 variants)

  • Baseline (no handle)
  • /no_think (underscore)
  • /no think (space)
  • /think (force thinking)

API Body Parameters (7 variants)

  • Baseline (no extra params)
  • enable_thinking=false
  • enable_thinking=true
  • thinking_budget=0
  • thinking_budget=128
  • chat_template_kwargs.enable_thinking=false
  • chat_template_kwargs.enable_thinking=true

Critical constraint: max_tokens=300 was applied to the entire completion — both reasoning tokens and visible response tokens competed for the same 300-token budget. This turned out to be a major confounding factor.

// The Token Budget Problem

Why 300 Tokens Wasn't Enough

Qwen3.5:9B generates hidden reasoning before producing a visible answer. Both compete for the same max_tokens budget. In 24 of 28 cases, reasoning consumed the entire 300 tokens before a visible answer could begin.

Best performer — Case 27: /think in system prompt + chat_template_kwargs.enable_thinking=false in the API body. This paradoxical combination — explicitly enabling thinking via the handle, then disabling it via the template parameter — produced the lowest reasoning overhead (75 tokens) and the most visible output (225 tokens). The mechanism is not well understood and should not be relied upon.

Counter-intuitive finding: /no_think + enable_thinking=false (Case 9) produced zero visible output, while /no_think + enable_thinking=true (Case 10) was one of only four cases that answered. The parameters appear to interact with the chat template in non-obvious ways that the endpoint does not document.

// Analysis

Key Findings

01

Reasoning_content appeared in all 28 cases

Even when every documented method for disabling thinking was applied, the model still produced reasoning_content via the API response field. Thinking was never truly off — it was merely hidden from the visible response text.

02

Qwen3.5 dropped /think and /nothink soft-switches

Qwen3 (the prior version) supported /think and /no_think as in-prompt toggle commands. Qwen3.5 removed official support for these soft-switches. The endpoint accepts them silently without error — giving false confidence that the command was processed.

03

The /no think variant (with space) never worked

All 7 cases using /no think (space instead of underscore) failed entirely. For Qwen3, the correct token sequence was /no_think with underscore. The space variant was always incorrect. The /no_think variant had partial success, but only with certain API body combinations.

04

Token budget starvation was the primary failure mode

In 24 of 28 cases, reasoning consumed exactly 299 of the 300 available tokens, leaving only 1 token for the visible answer. Increasing max_tokens to ≥900 is necessary to distinguish true control failures from budget starvation. Results under 300 tokens cannot be interpreted as a reliable measure of thinking control.

05

Parameter interactions are unpredictable

Some combinations that should logically disable thinking (e.g. /no_think + enable_thinking=false) produced worse results than combinations that shouldn't (e.g. /think + enable_thinking=false). This suggests the LM Studio server applies these parameters inconsistently or in an undocumented order of precedence.

// Recommended Next Steps

What to Try Next

Step 1 — Rerun with higher token budget. Repeat a representative subset of cases with max_tokens=900 or higher. This separates true control failures from budget starvation, which was the dominant failure mode in this experiment.

Example — Closest to working (Case 27 pattern)
# The best-performing pattern from this experiment
response = client.chat.completions.create(
    model="qwen/qwen3.5-9b",
    messages=[
        {"role": "system",
         "content": "/think You are a tourist guide..."},
        {"role": "user",
         "content": "Best way to explore Sydney in one day?"}
    ],
    max_tokens=900,  # ← critical change
    extra_body={
        "chat_template_kwargs": {
            "enable_thinking": False
        }
    }
)

Also worth testing

  • Ollama as backend instead of LM Studio
  • vLLM with --enable-reasoning-parser off
  • Different GGUF quantization level
  • /no_think in user message (not system) — untested here, reportedly more reliable for Qwen3

What to measure

  • Reasoning token count vs. visible tokens
  • Whether reasoning_content is present at all
  • Latency difference (thinking vs. no-thinking)
  • Answer quality, not just token count
// Conclusion

What This Tells Us

Under LM Studio's OpenAI-compatible API, Qwen3.5:9B does not offer reliable programmatic thinking control using the parameters tested here. Every tested control was silently accepted and silently ignored. The model always reasoned, and in most cases that reasoning consumed the entire output budget before a visible answer could be produced.

The primary takeaway for developers: if you're using Qwen3.5 locally, treat hidden reasoning as always-on and budget your max_tokens accordingly. Do not assume that enable_thinking=false or /no_think will suppress it. Monitor reasoning_content token usage and visible response token availability as your primary operational signals.

This experiment also highlights a documentation gap: Qwen3.5 dropped the soft-switch mechanism that Qwen3 supported, but the parameters are still accepted by some endpoints without raising errors. Community follow-up is needed to verify whether this behavior is specific to LM Studio's chat template implementation or is a broader property of the model weights.

// Limitations

What This Study Can't Tell You

Scope: One model, one runtime (LM Studio), one fixed prompt, one max_tokens setting. Results may differ significantly with a different LM Studio build, a different GGUF quantization, a different chat template, or a different serving backend (Ollama, vLLM, llama.cpp). Because the 300-token budget caused saturation in nearly all cases, conclusions about true thinking suppression remain tentative until a higher-token rerun is completed.
